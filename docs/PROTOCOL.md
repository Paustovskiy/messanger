# Протокол

Этот документ — для тех, кто захочет написать совместимый клиент (например, мобильный)
или просто разобраться, что именно летает по сети. Эталонная реализация — крейты
`protocol` и `crypto_core`; если документ и код расходятся, прав код (и это баг документа).

Все байтовые поля в JSON — **base64 без паддинга** (стандартный алфавит).
Паддинг `=` на входе допускается. Числа в канонических байтах — little-endian.

Схема шифрования повторяет Signal: [X3DH](https://signal.org/docs/specifications/x3dh/)
для первого знакомства и [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)
для переписки. Ниже — только то, чем наша реализация конкретизирует эти спецификации.

## 1. Ключи и идентификаторы

У аккаунта может быть до 10 **устройств**. Каждое устройство — отдельная пара ключей
`IK` + ключ подписи, свои предключи и свои сессии. Ключ подписи основного устройства
(№1) — это **ключ аккаунта**: им подписываются карточка контакта и список устройств (§4а).

| Ключ | Алгоритм | Живёт | Зачем |
|---|---|---|---|
| identity key (`IK`) | X25519 | всегда, у каждого устройства свой | участвует в X3DH |
| ключ подписи | Ed25519 | всегда, у каждого устройства свой | подпись предключей, конвертов, входа на релей; у устройства №1 — ещё карточки и списка устройств |
| подписанный предключ (`SPK`) | X25519 | меняется раз в 7 дней, старые хранятся 40 дней | X3DH, когда владелец офлайн |
| одноразовые предключи (`OPK`) | X25519 | до первого использования | X3DH: дополнительная защита первого сообщения |
| ratchet-ключи | X25519 | до следующего шага храповика | Double Ratchet |

`account_id` новых аккаунтов выводится из ключа подписи:
первые 16 байт `SHA-256("messenger/account-id/v1" ‖ ed25519_pub)` в hex (32 строчных символа).
Такой ID любой может проверить по ключу, поэтому его нельзя «занять» чужим ключом.

Старые аккаунты имеют `account_id` вида UUID v4. Протокол принимает любую строку
до 64 байт без управляющих символов; правило «ID должен совпадать с ключом» применяется
только к строкам ровно из 32 hex-символов.

**Отпечаток** (fingerprint) — первые 20 байт
`SHA-256("messenger/fingerprint/v1" ‖ IK_pub ‖ ed25519_pub)`
в hex, группами по 4 символа. Его сверяют голосом, чтобы убедиться, что карточка настоящая.
Отпечаток аккаунта считается по ключам основного устройства; у каждого устройства есть
и свой отпечаток — его сверяют при подключении устройства (§9).

## 2. Каноническое кодирование

Всё, что подписывается или идёт в AEAD как associated data, кодируется вручную:

- `bytes(x)` = длина `x` как `u64` LE ‖ сами байты;
- массивы фиксированной длины пишутся как есть, `u32` — 4 байта LE;
- `Option<T>`: `0x00` для `None`, `0x01 ‖ T` для `Some`.

## 3. Карточка контакта

```json
{
  "account_id": "c5d8e1ebe2adec8da57be884d10ea5a6",
  "username": "@bobby",
  "x25519_pub_b64": "...",
  "ed25519_pub_b64": "...",
  "sig_b64": "...",
  "signed_prekey": { "id": 1, "pub_b64": "...", "sig_b64": "..." }
}
```

Подпись Ed25519 над:

```
bytes(account_id) ‖ option(bytes(username)) ‖ x25519_pub[32] ‖ ed25519_pub[32]
```

(Байт-в-байт совпадает с прежним форматом `bincode 1`, поэтому старые карточки проверяются.)

Если `account_id` в формате «из ключа», он обязан совпадать с `ed25519_pub`.

`signed_prekey` необязателен и в подпись карточки не входит: он подписан сам (см. §4).
Он позволяет начать переписку без релея.

`devices` (необязательно) — подписанный список устройств аккаунта (§4а). Он тоже подписан
сам и в подпись карточки не входит.

Самоподпись доказывает только то, что карточку выпустил владелец ключа. Что этот ключ
принадлежит именно вашему собеседнику, доказывает лишь сверка отпечатков.

## 4. Предключи

Подписанный предключ: `{ id: u32, pub: [32], sig: [64] }`, где `sig` — Ed25519 над

```
"messenger/signed-prekey/v1" ‖ id ‖ pub
```

Одноразовый предключ: `{ id: u32, pub: [32] }`, без подписи (как в Signal: подмена OPK
не помогает атакующему, потому что в X3DH участвуют IK и подписанный SPK).

Предключ подписывает **устройство** своим ключом подписи. Получатель проверяет подпись
ключом этого устройства из списка устройств (или, если списка нет, из карточки
контакта) — **из своей базы**, а не из ответа релея.

## 4а. Список устройств

```json
{
  "account_id": "c5d8e1ebe2adec8da57be884d10ea5a6",
  "account_pub_b64": "<ключ аккаунта = ed25519 устройства №1>",
  "version": 3,
  "devices": [
    { "device_id": 1, "x25519_pub_b64": "...", "ed25519_pub_b64": "...", "name": "ноутбук" },
    { "device_id": 4, "x25519_pub_b64": "...", "ed25519_pub_b64": "...", "name": "телефон" }
  ],
  "sig_b64": "..."
}
```

Подпись Ed25519 ключом аккаунта над:

```
"messenger/device-list/v1" ‖ bytes(account_id) ‖ account_pub[32] ‖ version:u64
‖ count:u32 ‖ для каждого: device_id:u32 ‖ x25519_pub[32] ‖ ed25519_pub[32] ‖ bytes(name)
```

Правила (нарушение — список отвергается):

- от 1 до 10 устройств, отсортированы по `device_id` строго по возрастанию, `0` не используется;
- устройство №1 есть, и его `ed25519_pub` равен `account_pub`;
- `name` — до 32 символов, без управляющих;
- ключ аккаунта: если клиент уже знает его (из карточки контакта или прошлого списка),
  `account_pub` обязан совпасть; если нет — `account_id` обязан быть выведен из `account_pub`
  (§1). Список старого UUID-аккаунта без известного ключа не принимается;
- **версия только растёт.** Клиент и релей не принимают список с версией меньше уже
  виденной, а при равной версии — с другим содержимым. Так релей не может «вернуть»
  отключённое устройство, подсунув старый список.

Номера устройств не переиспользуются: новое получает `max(новая версия списка, max(device_id) + 1)`.
Версия растёт при каждом изменении списка, в том числе при отключении, поэтому номер
отключённого устройства (он всегда не больше версии на момент выдачи) не повторится.
Номера могут идти с пропусками. Это правило выдающего, подпись и проверка списка его не
требуют.

Об устройствах, которых нет в новом списке, клиент забывает: удаляет сессии с ними и
неотправленные им конверты.

## 5. X3DH

Алиса начинает сессию с Бобом, имея его `IK_B`, `SPK_B` и, возможно, `OPK_B`:

```
EK_A — свежая X25519-пара
DH1 = X25519(IK_A, SPK_B)
DH2 = X25519(EK_A, IK_B)
DH3 = X25519(EK_A, SPK_B)
DH4 = X25519(EK_A, OPK_B)          — если OPK был
SK  = HKDF-SHA256(salt = 0³², ikm = 0xFF³² ‖ DH1 ‖ DH2 ‖ DH3 [‖ DH4], info = "messenger/x3dh/v1", L = 32)
AD  = "messenger/x3dh-ad/v2" ‖ IK_A ‖ IK_B ‖ bytes(account_A) ‖ device_A:u32 ‖ bytes(account_B) ‖ device_B:u32
```

Любой DH, давший нули (low-order точка), — ошибка. `SPK_B` становится первым
ratchet-ключом Боба. Пока Алиса не получила от Боба ни одного сообщения, она прикладывает
к каждому своему конверту X3DH-заголовок `{ek_pub, spk_id, opk_id?}`.

Сессия заводится между **устройствами**: `IK_A`, `IK_B`, `SPK_B` и `OPK_B` — ключи
конкретных устройств.

Боб на первом сообщении берёт свои секреты по `spk_id`/`opk_id`, вычисляет тот же `SK`
и **сразу удаляет** использованный `OPK`. Он также запоминает `ek_pub` (в паре с
устройством-отправителем) и отклоняет повторное первое сообщение с тем же `ek_pub`.

## 6. Double Ratchet

По спецификации Signal, с такими функциями:

```
KDF_RK(rk, dh)  = HKDF-SHA256(salt = rk, ikm = dh, info = "messenger/ratchet-root/v1", L = 64) → (rk', ck)
KDF_CK(ck)      = (HMAC-SHA256(ck, 0x02) → ck',  HMAC-SHA256(ck, 0x01) → mk)
key ‖ nonce     = HKDF-SHA256(salt = 0³², ikm = mk, info = "messenger/ratchet-message/v1", L = 44)
body            = ChaCha20-Poly1305(key, nonce, plaintext, aad = AD ‖ header_bytes)
```

Ключ сообщения используется ровно один раз, поэтому детерминированный nonce безопасен.
`MAX_SKIP = 1000` на цепочку; пропущенных ключей храним не больше 2000 на сессию
(самые старые вытесняются).

### Несколько сессий с одним устройством

Принимаем через любую из последних 5 сессий, отправляем через текущую. Текущая меняется,
только когда появляется новая сессия:

- собеседник начал новую сессию — она становится текущей;
- но если мы сами начали свою и ещё не получили на неё ответа (одновременный старт),
  текущей остаётся сессия того, чья пара `(account_id, device_id)` меньше (строки
  сравниваются побайтово, затем номер устройства). Так сходятся и два устройства одного
  аккаунта.

Сообщение, пришедшее через старую сессию, читается, но текущую не меняет.

## 7. Конверт (v3)

Один конверт — одному **устройству**. Сообщение собеседнику с тремя устройствами — это
три конверта, плюс по копии на каждое своё другое устройство (§7а).

```json
{
  "v": 3,
  "from": "<account_id отправителя>",
  "from_device": 1,
  "to": "<account_id получателя>",
  "to_device": 2,
  "prekey": { "ek_pub_b64": "...", "spk_id": 1, "opk_id": 7 },
  "dh_pub_b64": "<текущий ratchet-ключ отправителя>",
  "pn": 0,
  "n": 3,
  "body_b64": "<шифротекст + 16 байт тега>",
  "sig_b64": "<64 байта>"
}
```

`prekey` есть только в первых сообщениях сессии; `opk_id` — только если использован OPK.

Канонический заголовок (он же — часть AAD):

```
header_bytes = "messenger/envelope-header/v3" ‖ 0x03 ‖ bytes(from) ‖ from_device:u32
             ‖ bytes(to) ‖ to_device:u32
             ‖ option(ek_pub[32] ‖ spk_id ‖ option(opk_id))
             ‖ dh_pub[32] ‖ pn ‖ n
```

Подпись Ed25519 (проверка строгая, `verify_strict`) над:

```
"messenger/envelope-sig/v3" ‖ bytes(header_bytes) ‖ bytes(body)
```

Подписывает **устройство-отправитель** своим ключом. Подпись нужна релею — чтобы
отсеивать подделки, не умея ничего расшифровать. Получатель тоже её проверяет, ключом
этого устройства **из своей базы** (список устройств или карточка контакта).

Открытый текст (§7а) — не больше 32 КиБ.

### 7а. Содержимое

Внутри шифротекста — JSON с полем `t`:

```json
{"t": "text", "id": "<32 hex>", "body": "Привет!"}
{"t": "sent", "id": "<32 hex>", "to": "<account_id собеседника>", "body": "Привет!"}
```

- `text` — сообщение собеседнику. `id` — случайный и общий для всех копий одного сообщения
  на разные устройства; по `(отправитель, id)` получатель хранит сообщение один раз.
- `sent` — копия сообщения, которое мы отправили `to` с другого своего устройства.
  Принимается **только от устройств своего же аккаунта**, иначе кто угодно мог бы
  приписать нам сообщения. И наоборот: `text` от своего же устройства отвергается.

Релей содержимого не видит и не отличает копию от обычного сообщения.

### Идентификатор сообщения

`msg_id` конверта = первые 16 байт `SHA-256("messenger/msg-id/v1" ‖ sig)` в hex (32 символа).
Получатель отбрасывает дубль по `(отправитель, устройство, msg_id)` **до** расшифровки:
ключ этого сообщения уже стёрт.

## 8. Протокол релея

JSON-сообщения поверх WebSocket (`/ws`), поле `type` — тип. Размер кадра — до 128 КиБ.
Релей адресует **устройства** `(account_id, device_id)`: у каждого своя очередь и свои
предключи. У устройства может быть несколько соединений одновременно; новые сообщения
релей отправляет во все.

### Вход

```
релей  → {"type":"challenge","nonce_b64":"<32 байта>"}
клиент → {"type":"auth","account_id":"...","device_id":1,"sign_pub_b64":"...","sig_b64":"..."}
релей  → {"type":"authenticated","account_id":"...","device_id":1}
         или {"type":"error","message":"..."} и закрытие
релей  → …накопившаяся очередь этого устройства (deliver / deliver_ack)…
релей  → {"type":"prekey_status","has_signed_prekey":true,"one_time_left":42,"device_list_version":3}
```

Подпись — ключом устройства над `"messenger/relay-auth/v2" ‖ nonce ‖ bytes(account_id) ‖ device_id:u32`.

- **Устройство №1** входит ключом аккаунта. Если `account_id` в формате «из ключа», релей
  проверяет, что он совпадает с `sign_pub`. Кроме того, первый успешный вход закрепляет
  `sign_pub` за `account_id` (TOFU), и дальше войти под этим `account_id` с другим ключом
  нельзя. Для старых UUID-аккаунтов это единственная защита.
- **Остальные устройства** релей пускает, только если `(device_id, sign_pub)` есть в
  последнем принятом списке устройств аккаунта.
- **Сессия ключом аккаунта** — `device_id = 0` (зарезервирован, в списке его не бывает).
  Вход только ключом, уже закреплённым за аккаунтом (привязку сессия не создаёт; для
  неизвестного аккаунта — ошибка `account key session needs a known account`). Это не
  устройство: релей отвечает `authenticated` и больше ничего не шлёт (ни очередь, ни
  `prekey_status`), письма на `(account, 0)` не принимает. Разрешены только
  `fetch_device_list` своего аккаунта и `publish_device_list` (с теми же проверками и
  рассылкой, что у обычной публикации); остальное — ошибка
  `not allowed in an account session`. Одновременных сессий на аккаунт не больше
  `max_connections_per_account`, считаются отдельно от обычных соединений.

На вход даётся 10 секунд.

`prekey_status` после входа приходит **после** всей очереди — это знак, что старые
сообщения выданы полностью. `device_list_version` — версия списка устройств аккаунта на
релее (нет поля — список ещё не публиковался). Основное устройство, увидев версию старее
своей, публикует свой список; остальные, увидев новее своей, запрашивают его.

### Список устройств

```
клиент → {"type":"publish_device_list","list":{...§4а...}}
релей  → {"type":"device_list","account_id":"...","list":{...}}
         (тот же ответ релей рассылает остальным устройствам аккаунта, что сейчас в сети)

клиент → {"type":"fetch_device_list","account_id":"..."}
релей  → {"type":"device_list","account_id":"...","list":{...}}   (без list — ещё не публиковался)
```

Публиковать список может только устройство №1. Релей проверяет подпись ключом вошедшего
(он же ключ аккаунта), структуру и версию (только рост; та же версия — только тот же
список). Для устройств, которых в новом списке нет (или чей номер теперь с другими
ключами), релей удаляет очередь и предключи, закрывает их соединения с ошибкой
`this device was removed from the account` и больше их не пускает.

Клиент перед отправкой запрашивает список устройств собеседника и свой, проверяет
подпись **сам** (релею не доверяет) и сохраняет только более новую версию.

### Предключи

```
клиент → {"type":"publish_prekeys","signed_prekey":{...},"one_time":[{"id":7,"pub_b64":"..."}, …]}
релей  → {"type":"prekey_status", …}

клиент → {"type":"fetch_bundle","account_id":"...","device_id":2}
релей  → {"type":"bundle","account_id":"...","device_id":2,"signed_prekey":{...},"one_time":{...}}
```

`publish_prekeys` заменяет подписанный предключ устройства и добавляет одноразовые (не
больше 100 за раз и 200 всего). Релей принимает только предключ, подписанный ключом
вошедшего устройства.
Клиент пополняет запас, когда одноразовых остаётся меньше 20, и публикует новый
подписанный предключ после ротации.

`bundle` выдаёт одноразовый ключ ровно один раз и сразу удаляет его. Если собеседник
ещё ничего не публиковал, `signed_prekey` отсутствует.

### Отправка

```
клиент → {"type":"send","to":"...","to_device":2,"msg_id":"...","envelope":{...конверт...}}
релей  → {"type":"accepted","msg_id":"..."}
         или {"type":"error","message":"...","msg_id":"..."}
```

Релей проверяет, что `(envelope.from, envelope.from_device)` — это вошедшее устройство,
`(envelope.to, envelope.to_device)` совпадает с `(to, to_device)`, конверт подписан ключом
отправителя, а у получателя такое устройство есть (№1 есть всегда, остальные — по списку;
иначе ошибка `recipient has no such device`, и клиент убирает конверт из исходящих).
Затем сохраняет конверт в очередь устройства (не больше 1000 сообщений на устройство,
хранение 30 дней).

### Доставка

```
релей  → {"type":"deliver","from":"...","from_device":1,"msg_id":"...","envelope":{...}}
клиент → {"type":"ack","to":"<отправитель>","to_device":1,"msg_id":"..."}
```

Конверт остаётся в очереди, **пока получатель не пришлёт `ack`**. Поэтому доставка
«хотя бы один раз»: при переподключении неподтверждённые сообщения приходят снова,
а клиент отбрасывает дубли.

Клиент подтверждает сообщение только после того, как сохранил его. Сообщение от
неизвестного отправителя клиент не подтверждает — оно ждёт на релее, пока
пользователь не добавит контакт. Подделки, повторы и битые сообщения клиент
подтверждает и выбрасывает, чтобы релей перестал их слать.

Если устройство-отправитель клиенту неизвестно, он сначала запрашивает свежий список
устройств отправителя и пробует снова. Если устройства нет и в свежем списке (его уже
отключили), проверить подпись нечем — сообщение подтверждается и выбрасывается.

### Уведомление о доставке

```
релей  → {"type":"deliver_ack","from":"<получатель>","from_device":2,"msg_id":"..."}
```

Пересылается устройству-отправителю (или ждёт его в очереди), только если
устройство-получатель действительно подтвердило реально ожидавший его конверт.
Клиент считает сообщение доставленным (✓✓), когда его подтвердило **любое** устройство
собеседника.

### Ограничения частоты

Сверх лимитов релей отвечает `{"type":"error","message":"rate limited, retry later"}`
(для `send` — с `msg_id`; сообщение у клиента остаётся в исходящих). Слишком частые
подключения с одного IP получают HTTP 429 ещё до WebSocket. Лишнее одновременное
соединение устройства получает ошибку при входе.

`fetch_bundle` сверх лимитов не ошибается: релей выдаёт набор **без** одноразового
ключа. Лимит есть и на запрашивающего, и на получателя: последний тратится, только
когда одноразовый ключ действительно выдан.

Лимиты отправок, публикаций (предключей и списков устройств) и запросов предключей
считаются на аккаунт — общие для всех его устройств. Бюджет одноразовых ключей
получателя — на устройство.

Значения по умолчанию: 60 подключений в минуту с IP, 10 одновременных соединений
устройства, 600 сообщений в минуту на соединение, 120 отправок в минуту, 30 публикаций
в час, 30 запросов предключей в минуту, 50 одноразовых ключей одного устройства в час.

### Поддержание соединения

Релей шлёт WebSocket-ping раз в 30 секунд. Если клиент молчит дольше 90 секунд
(не отвечает даже на ping), соединение закрывается.

## 9. Подключение нового устройства

Это делается вне релея, человек переносит данные сам (копированием, файлом):

1. **Новое устройство** заводит ключи и показывает код
   `mlink1.` ‖ base64url-без-паддинга(JSON `{"name","x25519_pub_b64","ed25519_pub_b64"}`)
   и свой отпечаток.
2. **Основное устройство** показывает отпечаток из кода; человек сверяет его с экраном
   нового устройства. Затем основное устройство выдаёт номер по правилу §4а,
   публикует новую версию списка и отдаёт ответ:

   ```json
   {"payload": "<JSON-строка>", "sig_b64": "..."}
   ```

   `payload` — `{"account_id","device_id","username","devices":{...§4а...},"contacts":[...]}`,
   где каждый контакт — `account_id`, `username`, ключи, необязательные `signed_prekey` и
   `devices`. Подпись — ключом аккаунта над `"messenger/link-response/v1" ‖ payload`
   (ровно байты строки).
3. **Новое устройство** проверяет список (§4а; для UUID-аккаунта ключ берётся из самого
   списка — тогда защитой служит только сверка отпечатка аккаунта), подпись ответа и что
   в списке под `device_id` именно его ключи. После этого оно — устройство аккаунта.

В ответе нет ни одного секрета: ключи аккаунта и история на новое устройство не
переносятся. Контакты, добавленные позже, на других устройствах сами не появляются.

Отключить устройство — это опубликовать новую версию списка без него (§8, «Список устройств»).
