# Протокол

Этот документ — для тех, кто захочет написать совместимый клиент (например, мобильный)
или просто разобраться, что именно летает по сети. Эталонная реализация — крейты
`protocol` и `crypto_core`; если документ и код расходятся, прав код (и это баг документа).

Все байтовые поля в JSON — **base64 без паддинга** (стандартный алфавит).
Паддинг `=` на входе допускается. Числа в канонических байтах — little-endian.

Схема шифрования повторяет Signal: [X3DH](https://signal.org/docs/specifications/x3dh/)
для первого знакомства и [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)
для переписки. Ниже — только то, чем наша реализация конкретизирует эти спецификации.

## 1. Ключи и идентификаторы

| Ключ | Алгоритм | Живёт | Зачем |
|---|---|---|---|
| identity key (`IK`) | X25519 | всегда | участвует в X3DH |
| ключ подписи | Ed25519 | всегда | подпись карточки, предключей, конвертов, входа на релей |
| подписанный предключ (`SPK`) | X25519 | меняется раз в 7 дней, старые хранятся 40 дней | X3DH, когда владелец офлайн |
| одноразовые предключи (`OPK`) | X25519 | до первого использования | X3DH: дополнительная защита первого сообщения |
| ratchet-ключи | X25519 | до следующего шага храповика | Double Ratchet |

`account_id` новых аккаунтов выводится из ключа подписи:
первые 16 байт `SHA-256("messenger/account-id/v1" ‖ ed25519_pub)` в hex (32 строчных символа).
Такой ID любой может проверить по ключу, поэтому его нельзя «занять» чужим ключом.

Старые аккаунты имеют `account_id` вида UUID v4. Протокол принимает любую строку
до 64 байт без управляющих символов; правило «ID должен совпадать с ключом» применяется
только к строкам ровно из 32 hex-символов.

**Отпечаток** (fingerprint) — первые 20 байт
`SHA-256("messenger/fingerprint/v1" ‖ IK_pub ‖ ed25519_pub)`
в hex, группами по 4 символа. Его сверяют голосом, чтобы убедиться, что карточка настоящая.

## 2. Каноническое кодирование

Всё, что подписывается или идёт в AEAD как associated data, кодируется вручную:

- `bytes(x)` = длина `x` как `u64` LE ‖ сами байты;
- массивы фиксированной длины пишутся как есть, `u32` — 4 байта LE;
- `Option<T>`: `0x00` для `None`, `0x01 ‖ T` для `Some`.

## 3. Карточка контакта

```json
{
  "account_id": "c5d8e1ebe2adec8da57be884d10ea5a6",
  "username": "@bobby",
  "x25519_pub_b64": "...",
  "ed25519_pub_b64": "...",
  "sig_b64": "...",
  "signed_prekey": { "id": 1, "pub_b64": "...", "sig_b64": "..." }
}
```

Подпись Ed25519 над:

```
bytes(account_id) ‖ option(bytes(username)) ‖ x25519_pub[32] ‖ ed25519_pub[32]
```

(Байт-в-байт совпадает с прежним форматом `bincode 1`, поэтому старые карточки проверяются.)

Если `account_id` в формате «из ключа», он обязан совпадать с `ed25519_pub`.

`signed_prekey` необязателен и в подпись карточки не входит: он подписан сам (см. §4).
Он позволяет начать переписку без релея.

Самоподпись доказывает только то, что карточку выпустил владелец ключа. Что этот ключ
принадлежит именно вашему собеседнику, доказывает лишь сверка отпечатков.

## 4. Предключи

Подписанный предключ: `{ id: u32, pub: [32], sig: [64] }`, где `sig` — Ed25519 над

```
"messenger/signed-prekey/v1" ‖ id ‖ pub
```

Одноразовый предключ: `{ id: u32, pub: [32] }`, без подписи (как в Signal: подмена OPK
не помогает атакующему, потому что в X3DH участвуют IK и подписанный SPK).

Получатель проверяет подпись предключа ключом Ed25519 собеседника **из своей базы
контактов**, а не из ответа релея.

## 5. X3DH

Алиса начинает сессию с Бобом, имея его `IK_B`, `SPK_B` и, возможно, `OPK_B`:

```
EK_A — свежая X25519-пара
DH1 = X25519(IK_A, SPK_B)
DH2 = X25519(EK_A, IK_B)
DH3 = X25519(EK_A, SPK_B)
DH4 = X25519(EK_A, OPK_B)          — если OPK был
SK  = HKDF-SHA256(salt = 0³², ikm = 0xFF³² ‖ DH1 ‖ DH2 ‖ DH3 [‖ DH4], info = "messenger/x3dh/v1", L = 32)
AD  = "messenger/x3dh-ad/v1" ‖ IK_A ‖ IK_B ‖ bytes(account_A) ‖ bytes(account_B)
```

Любой DH, давший нули (low-order точка), — ошибка. `SPK_B` становится первым
ratchet-ключом Боба. Пока Алиса не получила от Боба ни одного сообщения, она прикладывает
к каждому своему конверту X3DH-заголовок `{ek_pub, spk_id, opk_id?}`.

Боб на первом сообщении берёт свои секреты по `spk_id`/`opk_id`, вычисляет тот же `SK`
и **сразу удаляет** использованный `OPK`. Он также запоминает `ek_pub` (в паре с
отправителем) и отклоняет повторное первое сообщение с тем же `ek_pub`.

## 6. Double Ratchet

По спецификации Signal, с такими функциями:

```
KDF_RK(rk, dh)  = HKDF-SHA256(salt = rk, ikm = dh, info = "messenger/ratchet-root/v1", L = 64) → (rk', ck)
KDF_CK(ck)      = (HMAC-SHA256(ck, 0x02) → ck',  HMAC-SHA256(ck, 0x01) → mk)
key ‖ nonce     = HKDF-SHA256(salt = 0³², ikm = mk, info = "messenger/ratchet-message/v1", L = 44)
body            = ChaCha20-Poly1305(key, nonce, plaintext, aad = AD ‖ header_bytes)
```

Ключ сообщения используется ровно один раз, поэтому детерминированный nonce безопасен.
`MAX_SKIP = 1000` на цепочку; пропущенных ключей храним не больше 2000 на сессию
(самые старые вытесняются).

### Несколько сессий с одним собеседником

Принимаем через любую из последних 5 сессий, отправляем через текущую. Текущая меняется,
только когда появляется новая сессия:

- собеседник начал новую сессию — она становится текущей;
- но если мы сами начали свою и ещё не получили на неё ответа (одновременный старт),
  текущей остаётся сессия того, чей `account_id` меньше (побайтовое сравнение строк).

Сообщение, пришедшее через старую сессию, читается, но текущую не меняет.

## 7. Конверт (v2)

```json
{
  "v": 2,
  "from": "<account_id отправителя>",
  "to": "<account_id получателя>",
  "prekey": { "ek_pub_b64": "...", "spk_id": 1, "opk_id": 7 },
  "dh_pub_b64": "<текущий ratchet-ключ отправителя>",
  "pn": 0,
  "n": 3,
  "body_b64": "<шифротекст + 16 байт тега>",
  "sig_b64": "<64 байта>"
}
```

`prekey` есть только в первых сообщениях сессии; `opk_id` — только если использован OPK.

Канонический заголовок (он же — часть AAD):

```
header_bytes = "messenger/envelope-header/v2" ‖ 0x02 ‖ bytes(from) ‖ bytes(to)
             ‖ option(ek_pub[32] ‖ spk_id ‖ option(opk_id))
             ‖ dh_pub[32] ‖ pn ‖ n
```

Подпись Ed25519 (проверка строгая, `verify_strict`) над:

```
"messenger/envelope-sig/v2" ‖ bytes(header_bytes) ‖ bytes(body)
```

Подпись нужна релею — чтобы отсеивать подделки, не умея ничего расшифровать.
Получатель тоже её проверяет, ключом отправителя **из своей базы контактов**.

Открытый текст — не больше 32 КиБ, UTF-8.

### Идентификатор сообщения

`msg_id` = первые 16 байт `SHA-256("messenger/msg-id/v1" ‖ sig)` в hex (32 символа).
Получатель отбрасывает дубль по `(отправитель, msg_id)` **до** расшифровки:
ключ этого сообщения уже стёрт.

## 8. Протокол релея

JSON-сообщения поверх WebSocket (`/ws`), поле `type` — тип. Размер кадра — до 128 КиБ.
У аккаунта может быть несколько соединений одновременно; новые сообщения релей
отправляет во все.

### Вход

```
релей  → {"type":"challenge","nonce_b64":"<32 байта>"}
клиент → {"type":"auth","account_id":"...","sign_pub_b64":"...","sig_b64":"..."}
релей  → {"type":"authenticated","account_id":"..."}
         или {"type":"error","message":"..."} и закрытие
релей  → …накопившаяся очередь (deliver / deliver_ack)…
релей  → {"type":"prekey_status","has_signed_prekey":true,"one_time_left":42}
```

Подпись — над `"messenger/relay-auth/v1" ‖ nonce ‖ bytes(account_id)`.
Если `account_id` в формате «из ключа», релей проверяет, что он совпадает с `sign_pub`.
Кроме того, первый успешный вход закрепляет `sign_pub` за `account_id` (TOFU), и дальше войти
под этим `account_id` с другим ключом нельзя. Для старых UUID-аккаунтов это единственная защита.
На вход даётся 10 секунд.

`prekey_status` после входа приходит **после** всей очереди — это знак, что старые
сообщения выданы полностью.

### Предключи

```
клиент → {"type":"publish_prekeys","signed_prekey":{...},"one_time":[{"id":7,"pub_b64":"..."}, …]}
релей  → {"type":"prekey_status", …}

клиент → {"type":"fetch_bundle","account_id":"..."}
релей  → {"type":"bundle","account_id":"...","signed_prekey":{...},"one_time":{...}}
```

`publish_prekeys` заменяет подписанный предключ и добавляет одноразовые (не больше 100 за
раз и 200 всего). Релей принимает только предключ, подписанный ключом вошедшего аккаунта.
Клиент пополняет запас, когда одноразовых остаётся меньше 20, и публикует новый
подписанный предключ после ротации.

`bundle` выдаёт одноразовый ключ ровно один раз и сразу удаляет его. Если собеседник
ещё ничего не публиковал, `signed_prekey` отсутствует.

### Отправка

```
клиент → {"type":"send","to":"...","msg_id":"...","envelope":{...конверт...}}
релей  → {"type":"accepted","msg_id":"..."}
         или {"type":"error","message":"...","msg_id":"..."}
```

Релей проверяет, что `envelope.from` — это вошедший клиент, `envelope.to` совпадает с `to`
и конверт подписан ключом отправителя. Затем сохраняет его в очередь получателя
(не больше 1000 сообщений на получателя, хранение 30 дней).

### Доставка

```
релей  → {"type":"deliver","from":"...","msg_id":"...","envelope":{...}}
клиент → {"type":"ack","to":"<отправитель>","msg_id":"..."}
```

Конверт остаётся в очереди, **пока получатель не пришлёт `ack`**. Поэтому доставка
«хотя бы один раз»: при переподключении неподтверждённые сообщения приходят снова,
а клиент отбрасывает дубли.

Клиент подтверждает сообщение только после того, как сохранил его. Сообщение от
неизвестного отправителя клиент не подтверждает — оно ждёт на релее, пока
пользователь не добавит контакт. Подделки, повторы и битые сообщения клиент
подтверждает и выбрасывает, чтобы релей перестал их слать.

### Уведомление о доставке

```
релей  → {"type":"deliver_ack","from":"<получатель>","msg_id":"..."}
```

Пересылается отправителю (или ждёт его в очереди), только если получатель
действительно подтвердил реально ожидавшее его сообщение.

### Поддержание соединения

Релей шлёт WebSocket-ping раз в 30 секунд. Если клиент молчит дольше 90 секунд
(не отвечает даже на ping), соединение закрывается.
